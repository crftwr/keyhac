# AI 連携

[English](ai-integration.md) \| 日本語

> ## このページの URL を AI エージェントに渡す
>
> Keyhac のスキルと MCP サーバーのセットアップを頼めば、エージェントはここから大部分を
> こなせます。エージェントは下の [セットアップ](#セットアップ) を読みます。この節は
> エージェント向けに書かれていて、あなたにしかできない部分はエージェントがあなたに頼みます。
> あなた自身がこの手順に従う必要はありません。
>
> Keyhac のトレイメニューにリンクがあります。**AI Integration → Setup Guide** で、
> 実行中のバージョンに固定されたページが開きます。

Keyhac はそのツールを MCP で公開できます。チャットウィンドウでやりたいことを頼むと、
エージェントが実行中の Keyhac に対してそれを実行します。できることは 2 種類です。
**キーの動作を変えること**（キーテーブルと `config.py` を読み、変更を書き戻し、再読み込みします）と、
**アクションを書くこと** です。アクションを書くときエージェントは、セレクターを当て推量して
デバッグの必要なコードを渡すのではなく、実際の画面を調べ、コードを書き、実行し、
エラーを読み、修正します。

後に残るのは、あなた自身のファイルの中のただの Python です。後でキーを押したときに
モデルが動くことはありません。

MCP はオープンなプロトコルで、ここに特定のベンダーに依存するものはありません。どのクライアントも
`keyhac-mcp-bridge` コマンドを通じて同じ方法で接続します。クライアントが stdio MCP サーバーを
登録できるならそれとして、できないなら [シェルから直接実行](#シェルはあるが-mcp-トランスポートのないクライアント) して
使います。どちらかができるものなら動くはずです。[試したクライアント](#試したクライアント)
はそれより短いリストです。

**これは有効にしない限りオフです**。有効にする前に理由を理解しておく価値があります。
エンドポイントは開いているすべてのアプリケーションのアクセシビリティツリーを読み、
登録したアクションを実行できます。[セキュリティ](#セキュリティ) を参照してください。

> ### 2.2.0 または 2.2.1 からのアップグレード
>
> この機能を作る途中で 2 つの呼び出しが削除されました。どちらかをまだ呼んでいる `config.py`
> は読み込みに失敗します。失敗ははっきり表示され、修正するまでは以前の設定が有効なままです。
>
> - **`keymap.enable_mcp_server()`** — エンドポイントは今はチェックボックスです。
>   後述の **AI Integration > MCP Server** です。
> - **`keymap.register_action()`** — `~/.keyhac/extensions/` にあるアクションクラスは
>   登録なしで `module.Class` として呼び出せるので、この呼び出しにはもう役目がありません。
>   その行を削除してください。キー割り当てはもともとこれを経由しておらず、影響はありません。
>
> ```python
> import open_issues
> kt["Fn-I"] = open_issues.OpenIssues()      # this is all it ever needed
> ```

## 有効にする

コンソールウィンドウの **AI Integration: MCP Server** にチェックを入れるか、
トレイ / メニューバーのメニューで **AI Integration → MCP Server** を選びます。コンソールには
選ばれたポートが表示され、以降エージェントの呼び出しごとに 1 行、どのツールをどの引数で呼び、
どれだけの大きさの応答を返したかが記録されます。

```
INFO [keyhac.MCP] describe_screen(app='Chrome') -> 4812 chars
INFO [keyhac.MCP] write_extension(name='translate_clipboard', source='import ...') -> 118 chars
```

要約ではなく、各リクエストと応答の全体を見るには、コンソールのレベルを **Debug** にします。
エンベロープは 1 行のまま、ペイロードはその下にそのまま出力されるので、画面のダンプは
ツリーとして読めます。

```
DEBUG [keyhac.MCP] <- {"jsonrpc":"2.0","id":4,"result":{"content":[{"type":"text","text":"<result.content[0].text>"}],"isError":false}}
AXWindow 'my-projects (Workspace)'
  AXGroup 'my-projects (Workspace)'
    AXWebArea 'my-projects (Workspace)'
      AXStaticText = 'Diff editor'
```

**60 分経つと自動的にオフになり**、再起動をまたいで記憶されることもありません。必要なときに
もう一度チェックを入れてください。それが意図したリズムであり、回避すべき不便ではありません。

そうでないセッション、たとえば遅いシステムを午後いっぱい操作するアクションや長いオーサリング作業には、
**AI Integration > No timeout** で期限を外せます。外れるのはタイマーだけです。Keyhac を終了すれば
エンドポイントは閉じ、次の起動時にもオフのままです。その設定は記憶されますが、このスイッチは
意図的に記憶されないからです。作業の途中でエンドポイントが止まる損失が、それによる保護を上回るときに
使い、そのセッションが終わったらオフにしてください。

理由はこの機能の性質にあります。エージェントはアクションを *書く* のを手伝い、その後アクションは
モデル抜きで動きます。翌朝もまだ待ち受けているエンドポイントは何の役にも立っていません。
それでいて、開いているすべてのウィンドウを読むことはでき、それがこの機能にできる最も大きなことです。
オフにするのを覚えておく必要があるスイッチは、オフにされないものです。

タイムアウトはチェックを入れた時点から固定で、使っても延長されません。そのため、
エンドポイントを操作している何かが、定期的に動き続けることで自分の権限を開いたままにしておく
ことはできません。

これには意図的に設定 API がありません。すべてのウィンドウを読み、アクションのコードを書いて
実行できるエンドポイントは、オンかオフかが目に見えるべきです。数百行ある `config.py` の途中の
1 行は、かつて何が求められたかを示すだけで、今何が本当なのかは何も示しません。同じ考え方は
すでにキーボードフックにも適用されていて、フックは昔から設定ではなくチェックボックスです。
*（2.2.0 にはこのための `keymap.enable_mcp_server()` 呼び出しがありました。これは削除されたので、`config.py` からその行を消してスイッチを使ってください。）*

### 有効にするとエージェントにできること

画面を読むことに加えて、次のことができます。

- **アクションのモジュールを `~/.keyhac/extensions/` に保存する**。毎回コピーするための
  ソースを渡すのではなく、保存します。
- **そこで見つけたアクションクラスを実行する**。`module.Class` で指定し、`config.py` に
  エントリは一切要りません。
- **`config.py` を編集する**。読み、変更を入れて書き戻し、再読み込みします。リマップ、
  アプリケーションごとのキーテーブル、アクションをキーに割り当てる 2 行など、頼めば
  貼り付けるものとして返ってくるのではなく、ファイルに入ります。

アクションは `extensions/` 以下のファイルにある `ThreadedAction` のサブクラスで、
エージェントはそのすべてを一覧し、開始できます。登録も、別のカテゴリーも、同期させておくべきものも
ありません。

`config.py` はパッチではなく常にファイル全体が書き込まれるので、エージェントはまずそれを読み、
変更を最小限にするよう指示されています。**Keyhac は置き換えた版を** `.bak-<timestamp>` として
隣に残し、書き込みのたびに `+N/-M` の行数とともにコンソールに記録します。望まない書き換えは
黙って起こるのではなく、目に見え、元に戻せます。

**一覧しても何も実行されません**。Keyhac はそれらのクラスをファイルのインポートではなく
解析によって見つけるので、書きかけの実験が並んだディレクトリも、何かがその名前を指定するまでは
何もしません。これは `extensions/` が昔から持っている性質です。`config.py` がインポートしない
モジュールは実行されません。

**キー割り当てはあなたのものです。ただし自分で入力する必要はもうありません**。エンドポイントが
開いている間、アクションクラスはチャットウィンドウから実行でき、どのキーにも割り当てられていません。
`config.py` が加えるのは、何も接続していなくても動き続ける、あなたが選んだキーです。その行は
どちらが書いてもかまいません。2 行を頼んで自分で貼り付けても、割り当てを頼んでエージェントに
書かせてもよく、どちらにしてもキーはあなたが指定したもので、あなたのファイルにあります。

## セットアップ

**この節は AI エージェントに向けて書かれています**。人が読んでいるならそのまま従うこともできますが、
URL を渡すほうが近道です。

**インストールは 2 つあり、どちらも他方を含みません**。片方だけ入れてしまうのがよくある失敗で、
その失敗の仕方は大きく異なります。スキルがあって接続がない場合、あなたはユーザーの画面が
見えないと正しく答えますが、それは機能が壊れているように見えます。接続があってスキルがない場合、
すべてが動いているように見え、あなたは `sleep` や画面座標を含むアクションを書き、
それは別のマシンで壊れます。

ホストが MCP サーバーやスキルをどうインストールするかは **あなた** の知識であり、このページは
ほとんど推測しません。以下は Keyhac が知っていてあなたが知り得ないことに加え、名前を挙げる価値が
あるほど一般的なホストについて、現時点で正しいことです。Claude Desktop の設定ファイルは
[stdio のみのクライアント向けのブリッジ](#stdio-のみのクライアント向けのブリッジ) に、Claude の
スキルのアップローダーは [スキルを追加する](#スキルを追加する) にあります。どちらの節もこの節の
後にあり、どちらもユーザーと同じくあなたのためのものです。

### 1. スキル

スキルは 1 つ、**`keyhac-<version>-skill.zip`** です。キーの動作を変えること（リマップ、
アプリケーションごとのキーテーブル、ワンショットモディファイアとユーザーモディファイア、
`config.py` の編集）と、*アクション*（別のアプリケーションの UI を操作する Python）を
書くことの両方を扱い、ユーザーが頼んだほうのリファレンスへあなたを案内します。実行中の
バージョンに対応するリリースにあります。タグはこのページを取得した URL の `blob/` の後の部分で、
すでに `v` が付いています。

```
https://github.com/crftwr/keyhac/releases/tag/<tag>
```

このホストがスキルを受け取る方法でインストールしてください。ただし、それは **ユーザーにしかできない手順** だと考えておいてください。ほとんどのホストでは、スキルは設定 UI からファイルを
アップロードして入れるもので、その背後にツールはありません。自分でやろうとしてこのラウンドを
費やさないでください。ユーザーにリンクと手順を渡し、それで何が得られるかを伝え、自分にできることを
進めてください。[スキルを追加する](#スキルを追加する) に、先にオンにしておく必要がある設定も含めて、
Claude での手順があります。

**ただし、このホストがスキルをファイルとして保持している場合** は、それはあなたの仕事です。
手順を返すのではなく、そのまま実行してください。Claude Code は
`~/.claude/skills/<name>/SKILL.md` を読むので、バンドルを `~/.claude/skills/keyhac/` に
展開すればインストールは完了です。判断の基準はホストの名前ではなく、ホストが参照する場所に
あなたが書き込めるかどうかなので、アップロードの手順だと決めつける前に確認してください。

バンドルは *そのバージョンの* API を説明しているので、バージョンが合わない場合は回避策をとるより
ユーザーに伝える価値があります。スキル自身もそれを確認します。`SKILL.md` にはパッケージ化された
バージョンが書かれていて、`get_focus` の末尾には実行中のバージョンが出ます（`keyhac: X.Y.Z`。
`describe_keymap` も冒頭に出します）。メジャーまたはマイナーバージョンが異なれば、対応する
バンドルをアップロードするようユーザーに伝えます。パッチバージョンの違いは無視します。
**Keyhac 2.6 より前はスキルが 2 つありました**。`keyhac-key-table-configuration` と
`keyhac-action-authoring` です。どちらかがインストールされていたら、このスキルを入れるときに
削除してください。古いスキルは同じ依頼に反応し、古い API を説明してしまいます。

### 2. 接続

まずユーザーにエンドポイントをオンにしてもらいます。Keyhac のトレイメニューの
**AI Integration → MCP Server**、またはコンソールウィンドウの **AI Integration: MCP Server**
チェックボックスです。既定ではオフで、あなた自身がオンにすることはできません。

次に、このホストがブリッジをどう実行するかを決めます。違いがあるのはこの点だけです。
MCP サーバーを子プロセスとして起動できるクライアントは `keyhac-mcp-bridge` を stdio サーバーとして
登録します。**Claude Desktop はこの種類** なので、あなたがそこにいるなら
[ブリッジ](#stdio-のみのクライアント向けのブリッジ) を設定します。サーバーをまったく登録できないが
コマンドは実行できるクライアントは、[同じブリッジを 1 回の呼び出しごとに
実行](#a-client-with-a-shell-but-no-mcp-transport) します。

- **HTTP ポートではなくブリッジを通じて接続してください**。Keyhac のエンドポイントの実体は
  ループバックの HTTP で、ブリッジはその上の薄いシムですが、クライアントをそのポートに直接
  向けるのはサポートされる構成ではありません。ポートとトークンは Keyhac が再起動するたびに変わるので、
  保存した HTTP のエントリは次にユーザーが Keyhac を終了したときに古くなり、トークンも使うためには
  持ち回る必要があります。ブリッジはリクエストごとにそれらを読み直すので、向け直す必要は一度も
  ありません。
- Keyhac は接続情報を、ユーザーの `config.py` の隣に `mcp.json` として公開します。Keyhac を別の
  設定ディレクトリで起動していない限り `~/.keyhac/mcp.json` です。あなたは Keyhac のコンソールを
  読めないので、ファイルがなければ探し回らずに、起動時に何が表示されたかをユーザーに尋ねてください。
- その中で重要なキーは `bridge` で、シムの絶対パスです。このインストールがコンソールスクリプトを
  生成しなかった場合（ソースチェックアウト）には **存在しない** ので、これがあるかどうかが
  そもそもクライアントを設定できるかどうかの判定になります。
- ブリッジは引数をとらず、そのファイルを自分で見つけます。GUI のクライアントはシェルの `PATH` を
  引き継がないので、たいていは絶対パスが必要です。
  [stdio のみのクライアント向けのブリッジ](#stdio-のみのクライアント向けのブリッジ) に、
  設定のスニペットと、インストールの種類ごとのパスの場所があります。

### 3. フォルダー

ユーザーに **`~/.keyhac`** （Windows では `%USERPROFILE%\.keyhac`）を渡してもらってください。
`config.py` と `extensions/` があるフォルダーです。あなた自身のファイルツールで扱えれば、
設定の変更は変わる行だけの編集で済みます。Keyhac のツールを通すと、毎回ファイル全体を読んで
送り返すことになります。これが推奨の構成で、スキルもこれを求めます。

- **Claude Desktop:** メッセージ欄の **+** ボタンから **Add folder** を選び、ホームフォルダーの
  `.keyhac` を選びます。macOS ではこのフォルダーは隠れているので、フォルダーの選択画面で
  **⌘⇧.** （Cmd-Shift-ピリオド）を押して表示させます。`.keyhac` フォルダーを会話にドラッグしても
  かまいません。
- **Claude Code**、またはすでにユーザーのファイルを読み書きできる他のエージェント: 何もする必要は
  ありません。`~/.keyhac/config.py` を読めることを確認してください。

それができない場合でも、すべては Keyhac のツール（`read_config`、`write_config`、
`read_extension`、`write_extension` など）を通じて動きます。これらのツールはまさにその場合のために
あります。

### 4. 進め方

- 他のアプリケーションの設定ファイルを編集する前に **バックアップ** し、ユーザーに変更を見せてください。
  **ファイルを書く手段がまったくない場合**（これは普通のことで、失敗ではありません）は、正確なパスと
  正確な JSON を示し、貼り付けてもらってください。ファイルを新しく作るのか、既存のものに
  マージするのかも伝えてください。
- **他のアプリケーションを終了したり再起動したりしないでください**。ユーザーに頼み、その後に何が
  見えるはずかを伝えてください。
- **再起動するクライアントがあなた自身の動いているクライアントなら**、再起動するとこの会話は
  終わります。Claude Desktop を終了すれば、あなたも一緒に終了します。ユーザーがそれを行う *前に*
  そう伝え、次にすべきことを残してください。新しいチャットを開いて `list_windows` を頼むことです。
  以下の確認はそこで行われることになります。
- **推測せず確認してください**。再起動後に `list_windows` を呼びます。ユーザー自身のウィンドウが
  返ってくれば成功です。ツールがなければ、原因を推測せずにそのまま伝えてください。また、このホストの
  設定ファイルのパスやスキーマに確信がなければ、もっともらしいものを書かずに尋ねてください。
- ここからできないことは、ユーザーに頼んでください。Claude Desktop では設定の編集そのものも
  それに含まれます。Claude Desktop には MCP サーバーのエントリを *追加* したり編集したりする方法がなく、
  削除する方法しかないからです。貼り付けはユーザーがするものと考え、手間を少なくしてください。
  ブリッジの絶対パスと、そのまま入れられる正確な JSON を用意します。

## 試したクライアント

| クライアント | トランスポート | 状況 |
|---|---|---|
| Claude Desktop | stdio → [ブリッジ](#stdio-のみのクライアント向けのブリッジ) | **macOS と Windows で検証済み** — `examples/actions/` のアクションはこれを通じて書かれ、macOS で書いたものが Windows でそのまま動きました |
| Claude Code | stdio → [ブリッジ](#stdio-のみのクライアント向けのブリッジ)、`claude mcp add` で登録 | **macOS で検証済み** — このページの URL だけでセットアップでき、会話の中でツールが応答します |
| VS Code Copilot | stdio → [`.vscode/mcp.json`](#vs-code-copilot-との連携) 経由の [ブリッジ](#stdio-のみのクライアント向けのブリッジ) | **macOS で検証済み** — チャットでツールが見つかり、使えます。ワークスペースの JSON 設定ファイル以外に UI は不要です |
| シェルはあるが MCP トランスポートのないクライアント | [ブリッジを 1 回の呼び出しごとに](#シェルはあるが-mcp-トランスポートのないクライアント) | **macOS で仕組みを検証済み** — `--tools` と `tools/call` はどちらもシェルから応答します。この方法でタスク全体を通して動かしたクライアントはまだありません |
| MCP をサポートするその他のもの | stdio サーバーとしての [ブリッジ](#stdio-のみのクライアント向けのブリッジ) | 動くはずですが **未検証** です |

「未検証」は、それらのクライアントを疑っているという意味ではありません。まだ誰もこのエンドポイントに
対して動かしていないということです。試したら、動いたかどうかにかかわらず、その結果が役に立つ報告です。

**Claude Code で検証したこと**: このページの URL を渡すことがセットアップのすべてでした。
Claude Code は両方のスキルを自分で `~/.claude/skills/` にインストールし（アップロードもユーザーの
手順もなし）、ブリッジをユーザースコープで登録し、接続しました。その後のセッションでは、ツールを
ネイティブのツールとして呼び出し、実際の応答を得ました。後半には *新しい* セッションが必要だった
ことに注意してください。セットアップを行ったセッションは、自分が登録したばかりのサーバーより
古かったのです。これはごく普通のことで、[進め方](#4-進め方) の最後の手順が新しい
セッションで確認するよう言っているのはこのためです。

**HTTP ポートへの直接接続は対象外です**。デーモンはベアラートークン付きのループバック HTTP を
確かに提供していて、それがブリッジの通信相手であり、[セキュリティ](#セキュリティ) で説明していますが、
このページがサポートする構成でも、試した構成でもありません。クライアントに必要なことは
すべてブリッジがすでに行います。ブリッジはリクエストのたびにポートとトークンを自分で見つけるので、
Keyhac が新しいポートで再起動しても変更は不要で、トークンをクライアントに渡したり会話の中で
繰り返したりする必要もありません。コマンドを実行できるクライアントなら、MCP サーバーを登録できるか
どうかにかかわらずブリッジを使えます。
[シェルはあるが MCP トランスポートのないクライアント](#シェルはあるが-mcp-トランスポートのないクライアント)
を参照してください。

### stdio のみのクライアント向けのブリッジ

Claude Desktop はローカルの MCP サーバーを子プロセスとして起動し、その標準入出力で JSON-RPC を
やりとりします。Keyhac はその子プロセスにはなれません。Keyhac はキーボードフックとフォーカスの
履歴を保持する常駐デーモンで、会話ごとに 2 つ目のコピーを動かせば、2 つ目のフックと 2 回目の
アクセシビリティの確認が必要になります。そこで `keyhac-mcp-bridge` が代わりに子プロセスとして動き、
すでに動いているデーモンに転送します。ブリッジは独自のツール定義を持ちません。ブリッジが一覧する
ものは、デーモンがツールを提供するのと同じコードから来ているので、両者がずれることはありません。

**スイッチがオフでも、クライアントは接続されたままです**。MCP クライアントは、サーバーの起動中に
エラーに遭うとそのサーバーを壊れたものとみなし、呼び出すのをやめます。そのため、最もよくある状態、
つまり Keyhac は動いているが MCP スイッチがオフという状態が、以前は「keyhac failed to connect」
として届き、説明は誰も読まない行にあり、チェックを入れた後にクライアントの再起動が必要でした。
現在はハンドシェイクが成功し、スイッチがオンでもオフでもブリッジは Keyhac のツールを一覧します。
オフのときにツールを呼ぶと、どのチェックボックスにチェックを入れればよいかが返ってきます。
チェックを入れてエージェントにもう一度試すよう伝えれば、同じ呼び出しが通ります。一覧は
変わっていないので、クライアントが MCP のツール一覧変更通知をサポートしているかどうかにかかわらず、
再読み込みも再起動も不要です。1 時間が過ぎた場合や、Keyhac が終了ではなく強制終了された場合も
同じ応答になります。どちらもクライアント側からは同じに見えます。

登録します。Settings → Developer → Edit Config、または
`~/Library/Application Support/Claude/claude_desktop_config.json` です。

```json
{
  "mcpServers": {
    "keyhac": { "command": "keyhac-mcp-bridge" }
  }
}
```

Claude Desktop を再起動します。完全に終了してください（⌘Q）。ウィンドウを閉じるだけでは設定は
再読み込みされません。

GUI アプリはシェルの `PATH` を引き継がないので、**たいていは絶対パスが必要です**。

パスは `~/.keyhac/mcp.json` に `bridge` として公開されているので、書き写すのではなくそこから
読んでください。Keyhac のコンソールも、起動時に「MCP server listening」の次の行にそれを表示します。
どちらも使えない場合は、Keyhac のインストール方法によって決まります。

| インストール | パス |
|---|---|
| macOS アプリバンドル | `/Applications/Keyhac.app/Contents/Resources/bin/keyhac-mcp-bridge` |
| Windows の zip / ポータブルバンドル | `Keyhac.exe` の隣の `keyhac-mcp-bridge.exe` |
| Windows の Microsoft Store 版 | `%LOCALAPPDATA%\Microsoft\WindowsApps\keyhac-mcp-bridge.exe` — 下記参照 |
| `pip install keyhac` | `which keyhac-mcp-bridge`、または仮想環境の `bin/` |
| ソースチェックアウト | `make install` で作られる `.venv/bin/keyhac-mcp-bridge` — Keyhac を `make run` で起動したときは `PATH` 上に *ない* ことに注意 |

```json
{
  "mcpServers": {
    "keyhac": {
      "command": "/Applications/Keyhac.app/Contents/Resources/bin/keyhac-mcp-bridge"
    }
  }
}
```

**Microsoft Store 版では、クライアントを `C:\Program Files\WindowsApps` の中に向けないでください**。その中のものは、パッケージに属さないプログラムからは起動できません。
パスをどう書いても Windows は「Access is denied」と答え、その間もファイル自体は問題なく
読めるので、Windows ではなく Keyhac の問題に見えてしまいます。結果として、クライアントが起動した
瞬間に消え、ログには何も残らない MCP サーバーになります。代わりに、Windows がパッケージ用に登録する
コマンドを使ってください。

```json
{
  "mcpServers": {
    "keyhac": {
      "command": "C:\\Users\\<you>\\AppData\\Local\\Microsoft\\WindowsApps\\keyhac-mcp-bridge.exe"
    }
  }
}
```

このディレクトリは `PATH` 上にあるので、`PATH` を引き継ぐクライアントなら単に
`keyhac-mcp-bridge` と書けます。どちらにしても、`~/.keyhac/mcp.json` には実行中のインストールの
正確なパスが公開されているので、これを書き写すのではなくそこから読んでください。
*（Keyhac 2.2.2 以前はここにパッケージ内のパスを公開していて、それは動きませんでした。2.2.3 で修正されています。）*

古い Windows のバンドルは `.exe` ではなく `keyhac-mcp-bridge.cmd` を同梱していました。これは
今もあり、今も動きます（今は転送するだけです）。そのため 2.2.0〜2.2.2 向けに書いた設定は
変更不要です。

ブリッジはデーモンと同じインストールのものである必要はありません。エンドポイントのファイルを読んで
転送するだけです。

**どのクライアントに登録した場合も、JSON を編集した後はクライアントを再起動してください**。
MCP の設定ファイルは、ファイルが変わったときではなくクライアントがサーバーを起動するときに
読まれるので、動いたままのクライアントは起動時のサーバー一覧を保ち続けます。`keyhac` のツールはなく、
エラーもなく、ログにも説明はありません。より限定的な再読み込み（サーバーのエントリの *Restart* や
ウィンドウの再読み込み）を用意しているクライアントもあり、どちらでもかまいません。クライアント全体の
再起動なら確実です。

### VS Code Copilot との連携

VS Code Copilot は MCP サーバーの設定に `.vscode/mcp.json`（ワークスペース）または `~/.copilot/mcp-config.json`（ユーザー）を使います。同じブリッジの仕組みがここでも使えます。

**ワークスペースの設定**（ソース管理にチェックイン）:
```json
{
  "servers": {
    "keyhac": {
      "type": "stdio",
      "command": "/Applications/Keyhac.app/Contents/Resources/bin/keyhac-mcp-bridge"
    }
  }
}
```

これをプロジェクトのルートの `.vscode/mcp.json` に置きます。ブリッジのパスは Keyhac のインストール方法によって異なります。

| インストール | パス |
|---|---|
| macOS アプリバンドル | `/Applications/Keyhac.app/Contents/Resources/bin/keyhac-mcp-bridge` |
| Windows（ポータブルまたは zip） | `C:\path\to\keyhac-mcp-bridge.exe` |
| Microsoft Store | `C:\Users\<you>\AppData\Local\Microsoft\WindowsApps\keyhac-mcp-bridge.exe` |
| Linux（pip） | `/path/to/venv/bin/keyhac-mcp-bridge` または単に `keyhac-mcp-bridge` |

**ユーザーの設定**（すべてのプロジェクト向け）:
すべての VS Code プロジェクトに適用されるユーザー単位の設定には、同じ JSON を `~/.copilot/mcp-config.json` に置きます。こちらはワークスペースの変更や再起動をまたいで残ります。

**その後 VS Code を再読み込みします**。どのクライアントとも同じく、ファイルはサーバーの起動時に
読まれるので、すでに開いていたウィンドウでは、VS Code の MCP サーバー一覧からサーバーを
再起動するまで Keyhac のツールは一覧されません。それでだめならウィンドウを再読み込みするか、
VS Code 自体を再起動してください。

ここでブリッジが役に立つ理由は Claude Desktop の場合と同じです。ブリッジはリクエストごとに `~/.keyhac/mcp.json` を読むので、Keyhac が再起動して新しいポートを選んでも設定は動き続けます。[HTTP ポートがこのページのサポートする構成でない](#試したクライアント) のはまさにこのためで、今日のポートに固定したものは、次に Keyhac が起動したときに古くなります。

### シェルはあるが MCP トランスポートのないクライアント

MCP サーバーをまったく登録できないが、コマンドは実行できるエージェントもあります。ブリッジは
そうしたエージェントにも 1 回の呼び出しごとに使えます。デーモンはセッションを保持せず、
各リクエストに個別に応答するので、最初に `initialize` のハンドシェイクを行う必要がないからです。
JSON-RPC を 1 行入れれば、1 行出てきます。

**このページの記憶に頼らず、ツールが何かを尋ねてください**:

```
keyhac-mcp-bridge --tools
```

これはデーモン自身のツール一覧を JSON で出力します。名前、説明、引数のスキーマで、18 個のツールで
約 10KB です。デーモンが MCP クライアントに提供するのと同じ一覧を、コピーではなくその場で
取得するので、存在しないツールを説明することはありません。Keyhac が動いていて **AI Integration > MCP Server** がオンである必要があります。そうでなければ標準エラー出力に理由を
説明して 0 以外の終了コードで終わり、それを解析するもののために標準出力は空のままにします。

**ツールを呼ぶには、リクエストをファイルに書いてリダイレクトで渡します**:

```
cat > /tmp/keyhac-request.json <<'JSON'
{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"list_windows","arguments":{}}}
JSON
keyhac-mcp-bridge < /tmp/keyhac-request.json
```

JSON を `echo` にインラインで書く方法は、引数に引用符、バックスラッシュ、非 ASCII 文字が
含まれるまでは動きます。しかしそれはほとんどのウィンドウタイトルとパスの半分に当てはまり、
そうなるとシェルの引用符のエラーとして失敗し、それが Keyhac のエラーのように見えます。
ファイルには引用符の規則がありません。

**各リクエストは 1 行にしてください**。トランスポートは改行区切りなので、複数行に整形した
リクエストは複数のリクエストになり、そのどれも正しい JSON ではありません。しかも失敗は
表に出ません。出力はなく、終了ステータスは 0 で、ツールが何も言うことがなかったかのように見えます。
JSON を書くものには `separators` や `-c` を渡してください。1 行のリクエストを複数ファイルに
入れるのはかまいません。複数の応答が順に返ってきます。

**シェルに `curl` があってもブリッジを使ってください**。HTTP ポートを直接操作するのは
[対象外](#試したクライアント) で、この場合がその理由をよく示しています。`curl` を使うと、
`mcp.json` を読み、そこからトークンを取り出し、それを持ち回ることになります。会話の中へ、
シェルの履歴へ、コマンドを記録するあらゆるものへ。トークンは、ローカルのどんなプロセスと
あなたの画面の内容との間にも立ちはだかるものです。ブリッジを通せば、トークンはマシンの
ファイルシステムの外に出ることはなく、Keyhac が新しいポートで再起動しても何も変更する必要は
ありません。

**クライアントがサポートしているなら、本来の MCP の登録を使ってください**。この方法では
同意の仕組みが失われます。ネイティブのツールとしてなら、クライアントは `write_config`、
`write_extension`、`delete_extension`、`start_action` について個別に確認を求められます。
これらのツールがスイッチの後ろにあるのは、まさにそのための設計です。シェルを通すと
それらはどれもただのコマンドになり、ツールを個別に制限するクライアントでも、画面を読むことと
設定を書き換えることを区別できなくなります。

## スキルを追加する

ツールは、画面に何があるか、設定に何があるかをエージェントに伝えます。スキルは、それをどう扱うかを
伝えます。スキルがないと、もっともらしく見えて後で失敗する作業になります。`sleep` と画面座標だらけの
アクションや、決して有効にならないテーブルに書かれたキー割り当てです。

スキルは 1 つ、**`keyhac-<version>-skill.zip`** で、両方の作業を扱います。キーの動作を変えること
（リマップ、アプリケーションごとのテーブル、ワンショットモディファイアとユーザーモディファイア、
`config.py` の編集）と、API のないシステムのために別のアプリケーションの UI を操作する Python である
*アクション* を書くことです。その `SKILL.md` は短い振り分け役で、それぞれの作業の知識は、
作業がそれを必要とするときにだけエージェントが読むリファレンスになっています。そのため両方を
持っていても、片方だけの場合とコストは変わりません。

**2.6 より前からアップグレードしますか？** 以前はスキルが 2 つありました。
`keyhac-key-table-configuration` と `keyhac-action-authoring` です。このスキルを追加するときに
それらを削除してください。残しておくと、同じ依頼に古い API で応え続けます。

**リリースから入手します**:

```
https://github.com/crftwr/keyhac/releases/tag/<tag>
```

`<tag>` は `v` の後に、Keyhac のコンソールが起動時に表示するバージョンを続けたものです。たとえば
`v2.2.1` です。実行中のバージョンに合わせてください。スキルが説明する API はそのリリースのものです。

**Keyhac をアップグレードしたら、新しいリリースのスキルもアップロードしてください**。
アップロードしたスキルはスナップショットで、Keyhac のバージョンには追従しません。スキルは
両者が違うことに気づきます。最初に、パッケージ化されたバージョンと Keyhac が報告するバージョンを
比べ、メジャーまたはマイナーバージョンが違えば、先に進む前に再アップロードするよう伝えます。
（エージェントでないスクリプトは、エンドポイントがオンの間、`~/.keyhac/mcp.json` の `version`
キーから実行中のバージョンを読めます。）

バンドルは Claude のスキルのアップローダーに合わせた形になっていて、その 2 つの要件を満たしています。
アーカイブのルートに `SKILL.md` があり、名前と説明を YAML フロントマターとして持っていることです。
現在の Claude では **Customize → Skills → + → Create skill → Upload a skill** で、
zip を選びます。メニューはリリースによって変わります。その手順が見当たらなければ、この行を信じるより
設定の中の **Skills** を探してください。

**先に「Code execution and file creation」をオンにしてください**。Settings → Capabilities で、
Team や Enterprise のプランでは管理者が組織に対して有効にします。スキルはこの上で動き、これが
オフの間はスキルがまったく表示されません。それはプランの制限のように見えますが、そうではありません。
アップロードが空振りしたように見える、よくある理由がこれです。スキルのスキャンが有効な Enterprise の
組織では、アップロードしたスキルは実行できるようになる前にスキャンもされます（1、2 分）。

*内容* は Claude 専用ではありません。展開すれば Markdown で、文書を渡せるエージェントなら
どれにでも渡せます。それで得られないのは、言われなくてもそれを参照する *習慣* で、それが
スキルの仕組みが提供する部分です。

（Keyhac そのものを開発していて、ソースチェックアウトからビルドする場合は、
`make skill-bundle` で同じ zip が `dist/` に作られます。）

**スキルは接続ではなく、どちらの手順も他方を含みません**。スキルは知識、つまり規則と API
リファレンスで、あなたのマシンに届く手段は持っていません。ツールは上で登録したブリッジから来ます。
スキルだけをアップロードすると、エージェントはウィンドウが見えないと正しく答えます。ツールだけを
接続すると、エージェントはウィンドウを見たうえで、`sleep` と画面座標を使うアクションや、
確認していない割り当てを書きます。

## エージェントにできること

| ツール | |
|---|---|
| `list_windows`, `get_focus` | 何が開いているか、何にフォーカスがあるか |
| `describe_screen` | ウィンドウの要素ツリーをインデントしたテキストで。またはその中のコンテナ 1 つだけ（`within=`） |
| `find_elements` | ロール / 名前 / identifier / テキストによる絞り込み検索。各一致を祖先のパスで位置づけ、一意かどうかと、何があれば一意になるかも示す |
| `read_text` | 要素のテキスト全体（ターミナルのスクロールバック、エディターのバッファー）。長いものは末尾から、範囲ごとに返る（`start=`） |
| `enable_content_access` | Chromium/Electron アプリにコンテンツを公開させる（macOS） |
| `describe_keymap` | キーテーブル、そのうち現在のフォーカスに一致するもの、それぞれが何を割り当てているか |
| `read_config`, `write_config` | `config.py` を読む、置き換える（バックアップを残す） |
| `list_actions` | `extensions/` のアクションクラス、実行中のもの、それぞれが前回どう終わったか |
| `start_action`, `get_action_result`, `cancel_action` | アクションを開始する（渡せば、その回だけのコンストラクター引数 `arguments` 付きで）、記録した内容を集める、止める |
| `list_extensions` | `extensions/` のファイル。アクションクラスを持たないヘルパーも含む |
| `read_extension` | モジュールをディスク上のまま読む |
| `write_extension` | モジュールを保存する（ファイル全体） |
| `delete_extension` | モジュールを退役させる。消去ではなく、隣のバックアップに名前を変える |
| `reload_config` | 編集した `config.py` を読み直し、エラーがあれば報告する |

どのツールにも個別の権限はありません。それは漏れではなく設計です。**エンドポイントが開いていることが権限であり**、開いているのはあなたがスイッチにチェックを入れている間の 1 時間だけです。監査すべき
名前の一覧も、中途半端に有効になったものもありません。スイッチがオフであることが *そのまま* 答えです。

どのアクションクラスにキーを割り当てるかは `config.py` が決めます。エージェントがどれを実行して
よいかは、もう `config.py` が決めるのではありません。それを決めるのはスイッチで、スイッチは期限切れに
なります。

表のファイル関連のツール（`read_config` から `delete_extension` まで）は、`~/.keyhac` に自分で
アクセスできないエージェントのためのものです。フォルダーを渡されていれば（[フォルダー](#3-フォルダー)）、
エージェントは `config.py` と `extensions/` を直接読み書きし、Keyhac にしか答えられないことにだけ
Keyhac のツールを使います。設定が読み込めるかどうかには `reload_config`、何を実行できるかには
`list_actions` です。

## ループ

これは長いほうである *アクションを書く* ためのループです。**キーの動作を変えるほうは短く済みます**。
頼めば、エージェントは `config.py` とキーテーブルを読み、変更を書き戻し、再読み込みして、
再読み込みの結果を報告し、キーを押してみるよう頼みます。画面から何かを調べる必要がないので、
画面を介した往復もありません。

1. アクションが対象とする画面を開きます。
2. やりたいことを自分の言葉で頼みます。アプリケーションと出力を挙げるのは役に立ちますが、
   API を挙げるのは役に立ちません。`find_element` と打ち込んでいる自分に気づいたら、教えてください。
   それはスキルがうまく働いていないということです。
3. エージェントは画面を読み、アクションを書き、`extensions/` に保存します。実行し、自分の失敗を読み、
   修正し、もう一度実行します。何回かかっても、**あなたはこの部分に関わりません**。
4. **動いたら、キーを割り当てます**。キーを指定すれば、エージェントは `config.py` に 2 行
   （`import` と割り当て）を書き、ファイルを再読み込みして、その結果を伝えます。自分でやりたければ、
   代わりにその行を頼んでください。どちらでも頼み方は同じ一文です。それから **キーを押してください**。
   それが正しく動くかどうかは、ほかの誰にも代わりに確かめられない唯一のことです。

1 時間を過ぎても残るのはステップ 4 だけです。それより前のものはすべて、チャットウィンドウからしか、
しかもエンドポイントが開いている間しか使えず、閉じれば意味を失います。割り当ては何も接続して
いなくても動き続けます。会話の中に置いておくのではなくファイルに書く意味はそこにあります。
ですから、目を通す価値があるのはこのステップです。そして Keyhac は、信用してくれと頼むのではなく、
それを可能にしています。置き換えられたファイルは隣に残り、書き込みは行数とともにコンソールに
出ます。

**Keyhac をアップグレードしたら再起動してください**。`reload_config` が再読み込みするのは
あなたの `config.py` で、Keyhac 自身のモジュールではありません。新しいバージョンのツールは再起動で
しか反映されません。（苦い経験から分かったことです。ツールの変更を実機で確かめた 2 回が、実際には
デーモンが起動したときのビルドをテストしていました。）

## 録画したデモンストレーションから作る

Claude Desktop は、タスク（画面、クリック、入力、そして **音声**）を録画してスキルに変えられます。
そのスキルはアクションへの良い *入力* になります。ただし重要な役割分担が 1 つあります。

- **録画は意図を提供します**。何をしようとしていたか、どの値が変わるか、繰り返しの区切りはどこか、
  次に進む前に何を確認したか。ナレーションが重要な半分です。クリックの記録だけでは、文字列を
  入力したことは分かっても、なぜかは分かりません。
- **ツールはセレクターを提供します**。録画にあるのはピクセルで、ピクセルで指定したアクションは
  失敗するアクションです。Claude はすべてのセレクターを `describe_screen` で実際のツリーから
  導き直します。

ですから流れはこうです。タスクを録画し、それから Claude に、そのスキルを *目の前の画面に対して*
Keyhac のアクションにするよう頼みます。始めるには普通の依頼で十分です（「I want to make a Keyhac
action from operations I capture with Record a skill」）。Claude は必要になったときに録画を求めます。
Claude はまず質問してくるはずです。録画からは、フィルターを「active」に設定したことは分かっても、
それが定数なのか引数なのかは分からないからです。

**録画しながら話してください**。何をしていて、なぜそうするのか、次回は何が変わりうるのか
（どの値が変わるか、何かがないときにどうすべきか）を話します。アクションが対処すべき微妙な点は
そうやって伝わります。クリックだけでは伝わりません。

**録画は Keyhac ではなく Anthropic のものです**。録画は Claude Desktop が自身の同意ダイアログの
もとで取得し、Claude に送られます。Keyhac はキーボードを録画することはなく、録画を読むことも
ありません。Claude Desktop の警告がそのまま当てはまります。録画中にパスワードを入力したり、
私的なものを表示したりしないでください。

## セキュリティ

- **既定ではオフ** で、スイッチは目に見えます。**AI Integration → MCP Server** にチェックを
  入れるまで何も待ち受けず、オンの間はチェックボックスとメニュー項目の両方がそれを示します。
  設定ファイルの 1 行にはそれができません。
- **ループバックのみ** で、起動のたびに生成されるトークンが、設定の隣の `mcp.json` に、あなただけが
  読める形で公開されます。ブリッジはそれを読みます。マシン上の他のプロセスは、それなしでは
  エンドポイントを使えません。
- **60 分経つと自動的に閉じ**、起動時に復元されることもありません。そのため、露出が続くのは
  あなたが忘れている間ではなく作業の間だけです。*No timeout* は、1 時間を超えるセッションのために
  前半を手放します。それでも後半が範囲を限り、終了すればそれで終わります。
- **すべての呼び出しはコンソールに出ます**。何かを変えたかどうかにかかわらず 1 回 1 行です。
  ウィンドウを読むことも、ファイルを書くのと同じように痕跡を残します。チャットウィンドウが見せるのは
  エージェントがあなたに伝えることにしたものですが、こちらはエージェントが実際に Keyhac に
  求めたものを見せます。
- **書き込めるのは 2 か所だけで、それ以外にはありません**。`~/.keyhac/extensions/` 以下の `.py`
  （名前はインポート可能なモジュール名でなければならず、それによってパスの指定やトラバーサルが
  排除されます）と、`config.py` そのものです。どちらも黙って置き換えられることはありません。
  以前の版は隣に `.bak-<timestamp>` として残り、書き込みはすべて `+N/-M` の行数とともにコンソールに
  記録されます。**何も消去されません**。`delete_extension` はモジュールを同じ `.bak-<timestamp>` に
  名前を変えて退役させるので、セッション後の片付けは名前を戻せば元に戻ります。
- **1 時間を過ぎても残るのは `write_config` だけです**。エージェントがここで行うほかのことはすべて、
  エンドポイントが閉じれば期限切れになります。`config.py` に書かれたキー割り当ては動き続け、
  それが書く意味です。これが `write_extension` とは別のツールになっているのは、その違いを引数の
  陰に隠さず、目に見えるようにするためです。
- **テキストを入力したりキーを押したりするものはありません**。ツリーを読むことと、チャットウィンドウ
  からキーボードを操作することは別の話で、後者はまだ決めていない判断です。
- **一覧してもインポートしません**。カタログはファイルを解析して作られるので、`extensions/` の中の
  ものは、何かがその名前を指定するまで実行されません。
- 同じスイッチでオフにします。そのときと Keyhac が停止したときに、トークンのファイルは削除されます。

### これで防げないもの

チェックを入れる前に知っておく価値があります。

`describe_screen` と `read_text` は、ウィンドウの内容（Web ページを含む）をモデルのコンテキストに
入れます。そのテキストは信頼できません。ページには、あなたではなく *エージェントに* 読まれるために
書かれたものが含まれていることがあります。オーサリングのスキルはエージェントに、画面の内容は
データであって決して指示ではないと伝えます。これは現実的な緩和策ですが、完全なものではありません。

ですからはっきり言っておきます。**エンドポイントが開いている間は、あなたが読んでいないコードが `extensions/` に書かれ、実行されることがあります**。スイッチが許可するのはそれであり、それは機能
そのもので、機能の穴ではありません。以前は、アクションを `config.py` に登録することが、
「エージェントがコードを書いた」と「コードが実行された」の間にある人間の手順でした。
エンドポイントが開いている間は、もうそうではありません。

そして `config.py` も書き込めます。これは 1 時間を超えて残ることを意図した唯一の書き込みです。
ですから、後で実際に読むべき変更はそこにあります。

それでも保たれていること: 書き込みは正確に 2 か所、つまりモジュール名による `extensions/` か
`config.py` のどちらかにしか行われず、どちらも黙って行われることはありません。以前の版は隣に残り、
書き込みは行数とともに記録されます。`extensions/` の中のものは、名前を指定されない限り実行されません。
そして **1 時間が過ぎればすべて止まります**。画面の読み取りも含めてです。残るのはあなたの
`config.py` で、書かれているとおりのことをします。

ですから現実的な答えは、あなたに任されるのではなく組み込まれています。露出はあなたが画面の前に
座っている時間と重なり、あなたは書き込みだけでなくすべての呼び出しを報告するコンソールを見ていて、
露出は自然に終わります。それは誰も読まない関門よりも価値があります。
